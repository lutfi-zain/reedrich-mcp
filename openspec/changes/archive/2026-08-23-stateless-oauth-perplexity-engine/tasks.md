## 4. Authorization, Token, and Protected Resource Gate

- [x] 4.1 Implement `GET /oauth/authorize` in `src/index.ts`: validate `response_type=="code"`, `client_id` present, `redirect_uri` is absolute HTTPS (or loopback HTTP) and — when `client_id` was issued with known `redirect_uris` — matches exactly (string equality); validate `code_challenge` present and `code_challenge_method=="S256"` (reject `plain` with `invalid_request`), `scope` in `scopes_supported` (or default `"mcp"`), authenticate user via `extractAuthenticatedUserId` (Bearer `rd_live_`/`fp_live_` or JWT or `?token=`), echo `state` verbatim, and on success issue authorization code JWT via `generateAuthorizationCode` (5-min expiry, `jti`) then `302` to `redirect_uri?code=<jwt>&state=<state>` with `Cache-Control: no-store, Pragma: no-cache`; on pre-redirect errors return `400` JSON, on post-validation errors redirect with `?error=&error_description=&state=`.
- [x] 4.2 Implement `POST /oauth/token` — `grant_type=authorization_code` branch: accept `application/x-www-form-urlencoded` (and lenient `application/json`), validate `code` (verify via `verifyAuthorizationCode`, reject expired with `invalid_grant`), validate `redirect_uri` equals code's `redirect_uri` (string equality), `client_id` equals code's `client_id`, validate `code_verifier` (require when code has `code_challenge`, check `isValidVerifier`, compute `computeS256Challenge` and constant-time compare to code's `code_challenge`, reject mismatch with `invalid_grant`), verify `client_secret` via `verifyClientSecret` when Basic or `client_secret` field present (reject with `401 invalid_client` + `WWW-Authenticate: Basic realm="oauth"` for Basic), then issue `access_token` (900s) + `refresh_token` (2592000s, new `jti`) and return `200` JSON `{access_token, token_type:"Bearer", expires_in:900, refresh_token, scope}` with `Cache-Control: no-store, Pragma: no-cache`.
- [x] 4.3 Implement `POST /oauth/token` — `grant_type=refresh_token` branch: validate `refresh_token` via `verifyRefreshToken` (HS256, `token_type=="refresh"`, expiry with 60s skew), validate `client_id` matches token's `client_id` (and `client_secret` if confidential), enforce `scope` is equal or narrower (subset) than original (reject broader with `invalid_scope`), issue rotated `access_token` (new `iat/jti`, 900s) + new `refresh_token` (new `iat/jti`, 2592000s), return `200` JSON same shape with `Cache-Control: no-store`; reject expired/tampered/access-token-as-refresh with `400 invalid_grant` (or `401 invalid_client` for secret failure), handle `unsupported_grant_type` and missing `grant_type` with `400 invalid_request`.
- [x] 4.4 Implement optional `POST /oauth/revoke` (stateless best-effort): accept `token` + `token_type_hint`, verify signature if JWT-shaped via `verifyOAuthAccessToken`/`verifyRefreshToken`, always return `200` with `Cache-Control: no-store` (no revocation list, document expiry-based revocation), no D1 writes.
- [x] 4.5 Implement protected resource gate on `/mcp` and `/sse`: before `handleMcpRequest` MCP transport, attempt (a) OAuth access JWT verify, (b) legacy Reedrich JWT verify (`verifyUserToken`), (c) `rd_live_`/`fp_live_` hash lookup (one D1 read allowed); on failure return `401` with `WWW-Authenticate: Bearer resource_metadata="https://<host>/.well-known/oauth-protected-resource", error="invalid_token"` (or `error="insufficient_scope"` when scope check fails), `Content-Type: application/json`, `Cache-Control: no-store, Pragma: no-cache`, `Access-Control-Allow-Origin: *`, and JSON `{error, error_description}`; on success set `userId` from `sub` and proceed to `createMCPServer` with RLS. Ensure reflection of `resource_metadata` uses `buildIssuerOrigin(c) + "/.well-known/oauth-protected-resource"`.
- [x] 4.6 Ensure backward compatibility: unauthenticated discovery (`/.well-known/*`, `/oauth/register`, `/health`, `/`, `/openapi.json`, `/privacy`) remain public; `POST /mcp` with valid `rd_live_` or legacy JWT still returns `200` MCP response (add integration test asserting both old and new bearers succeed).
